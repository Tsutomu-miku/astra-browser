# ADR-0021: Direct Chromium Patch Strategy

- Status: Accepted
- Date: 2026-06-12
- Deciders: Architecture

## Context

Astra is a direct Chromium overlay. The `//astra` directory contains all Astra-specific product code, but some integration points require small changes to Chromium source files (e.g., registering Astra's `BrowserMainExtraParts`, installing `AstraBrowserView` into `BrowserView`, forwarding command IDs to `AstraCommandDelegate`).

The key architectural question is how Astra integrates with Chromium without forking the project. The strategy must balance:
- Clean separation between Astra code and Chromium code.
- Ease of rebasing to new Chromium versions.
- Minimizing the number and size of patches.
- Making patches reviewable and documented.
- Ensuring upstream Chromium behavior is unchanged when Astra is not built.

## Decision

Astra uses an **overlay directory + minimal patch queue + delegation pattern** approach. All product logic lives in `//astra`; Chromium files receive only tiny patch points that delegate immediately into Astra code.

**Overlay directory (`chromium/astra/` -> `chromium/src/astra/`):**
- The `chromium/astra/` directory in the Astra repo is synced into `chromium/src/astra/` in the Chromium checkout.
- Astra code follows Chromium style, build system (GN/BUILD.gn), and directory conventions.
- The overlay is treated as a first-party Chromium directory (`//astra`) in the build graph.
- Sync is managed by `scripts/sync-chromium-overlay.sh`.

**Patch queue (`chromium/astra/patches/`):**
- Each patch is documented in a numbered detail file (`NNNN-patch-name.md`).
- Patches are applied in order during Chromium bootstrap / update.
- Patch files document: exact lines changed, surrounding context, rationale, alternatives considered, rebase risks.
- All patches are build-flag gated with `BUILDFLAG(IS_ASTRA_BRANDED)` so upstream behavior is unchanged when the flag is off.

**Patch rules:**
- **Minimal:** Each patch should be 1-50 lines. If a patch grows larger, move logic to `//astra`.
- **Delegation only:** Patches call into `//astra` and do nothing else. No product logic in patched files.
- **Build-flag gated:** All Astra code paths in Chromium files are guarded by the Astra build flag.
- **Documented:** Every patch has a detail file explaining what, why, and alternatives.
- **Numbered:** Patches are numbered sequentially in suggested application order.

**Delegation pattern (the "one if statement" rule):**
- The ideal patch is a single `if` statement or function call that routes to `//astra`.
- Example: in `BrowserCommandController::ExecuteCommand()`, after Chrome handles the command, add `if (IsAstraCommand(command_id)) astra::ExecuteAstraCommand(browser_, command_id);`.
- All actual logic, state, and computation live in `//astra` code.

**Rebase strategy:**
- When updating Chromium to a new revision, patches are rebased one by one.
- If a patch point no longer exists, find a new hook in Chromium or move logic to `//astra`.
- If a conflict requires a patch to grow significantly, re-evaluate the architecture.
- Patch conflict resolution order: 1) rebase cleanly, 2) move logic to `//astra`, 3) find new patch point, 4) escalate to ADR.

**Patch categories (from most to least acceptable):**
1. **Registration hooks** -- Adding Astra to a list of things that already exists (e.g., `BrowserMainExtraParts` list). Lowest risk.
2. **Observer / delegate hooks** -- Adding Astra as an observer or delegate in an existing observer pattern.
3. **Conditional forward calls** -- `if (astra) astra::DoThing()`. Small if-statements that call into Astra.
4. **Behavioral modifications** -- Changing existing Chromium behavior for Astra. Avoided unless absolutely necessary.

## Consequences

Positive:

- Clean separation: Astra code is in `//astra`, Chromium code is nearly pristine.
- Easy to review: patches are small and documented.
- Easy to rebase: few lines changed per patch, delegation pattern means patches are simple `if` statements or registrations.
- No fork: Chromium can be updated from upstream regularly.
- Build-flag gating means the default Chromium build is unaffected.
- Patch queue is transparent: every change to Chromium is documented and justified.

Negative:

- Some features may not have a clean hook point and require creative architecture to avoid large patches.
- Patch maintenance is ongoing overhead with every Chromium update.
- The overlay sync step adds complexity to the build workflow.
- Developers must be disciplined about keeping patches small and delegating to `//astra`.

Neutral:

- The patch queue currently lives as documentation files; actual `.patch` files are generated by tooling or applied manually. This can be improved with automated patch management.

## Alternatives Considered

### Full Chromium fork
Maintain a complete fork of Chromium with Astra changes merged in.

- Rejected: Makes it very hard to pull upstream Chromium updates. Security patches, new features, and bug fixes from upstream would require constant merge effort. The overhead is enormous for a small team.

### CEF (Chromium Embedded Framework)
Build Astra as a CEF client, using CEF's C API to embed Chromium.

- Rejected: CEF is designed for embedding web content in native apps, not for building a full browser product. Many Chrome features (extensions, password manager, safe browsing, DevTools protocol, WebUI) are limited or unavailable through CEF. Also rejected by project direction (AGENTS.md).

### Electron
Build Astra with Electron.

- Rejected: Electron does not expose the full Chrome browser stack. Many features (tab strip model, profile management, extensions) would need to be reimplemented. Also rejected by project direction (AGENTS.md).

### WebUI / extension overlay
Build Astra's UI as a WebUI or extension layer on top of Chrome.

- Rejected: Cannot deeply integrate with browser chrome, tab strip, and content area layout. Performance and capability limitations. Not a viable path for a product-level browser.
